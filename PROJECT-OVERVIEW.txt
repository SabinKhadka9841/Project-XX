PROJECT VAULT — WHAT'S IN THIS REPO AND HOW IT FITS TOGETHER
==============================================================
(Written for where the project stood after Phase 0, Prompts 1-4.
 If more prompts have been built since, this file may be out of date —
 ask Claude to regenerate it.)


THE ONE-SENTENCE VERSION
-------------------------
A student group builds their project inside Supabase (login + database
+ file storage); Next.js is the web app that lets them log in and,
eventually, copy/edit/approve each other's changes.


------------------------------------------------------------
1. PLANNING DOCS (not code — instructions Claude reads)
------------------------------------------------------------

CLAUDE.md
    The master brief. Says what we're building (a collaboration tool
    for student group projects), the rules that must never be broken
    (no custom editor, no file-format conversion, no dev jargon like
    "branch" or "commit" in the UI), the tech stack, the database
    shape, and the four build phases. Every prompt in BUILD-PROMPTS.md
    exists to implement something described in here.

BUILD-PROMPTS.md
    12 copy-paste prompts, in order, that were fed to Claude Code one
    at a time to actually build the app. Prompts 1-4 are done (see
    below). Prompts 5-12 build the rest: projects list, file upload,
    making copies, editing copies, requesting changes go in, approving
    them, invite links, and the contribution timeline.

TEAM-SPLIT.md
    A guide for splitting Phase 1 (prompts 7-12) across two developers
    once the schema is agreed — one person owns "the copy side," the
    other owns "the project side." Not yet relevant since Phase 0
    isn't finished.

AGENTS.md
    Auto-generated by the Next.js installer. Tells any AI coding tool
    (Claude Code included) to check node_modules/next/dist/docs before
    writing Next.js-specific code, since APIs change between versions.
    CLAUDE.md has a line at its very top ("@AGENTS.md") that pulls
    this file's rules in automatically.

README.md
    The standard boilerplate Next.js writes into every new project
    (how to run it, link to Next.js docs). Not customized yet.


------------------------------------------------------------
2. CONFIGURATION FILES (control how the app builds and runs)
------------------------------------------------------------

package.json
    The project's identity card: its name, and the dependencies it
    needs (next, react, the Supabase libraries). Also defines the
    shortcut commands — "npm run dev" starts it, "npm run build"
    creates a production version.

package-lock.json
    Auto-generated. Pins the *exact* version of every dependency (and
    every dependency of every dependency) so the project installs
    identically on any machine. Never hand-edited.

tsconfig.json
    TypeScript's settings. The important bit for this project: it
    defines "@/*" as a shortcut for "src/*", which is why files import
    things like "@/lib/supabase/client" instead of long relative paths
    like "../../lib/supabase/client".

next.config.ts
    Next.js's settings. Currently just fixes one thing: it pins the
    project's root directory explicitly, because a leftover
    package-lock.json in the Mac user's home folder was confusing
    Next's automatic root-detection and printing a warning on every
    build.

eslint.config.mjs
    Linting rules — checks the code for common mistakes as you write.

postcss.config.mjs
    Plumbing that lets Tailwind's CSS syntax work inside globals.css.

.gitignore
    Tells git which files to never track: node_modules (huge,
    regenerable), .next (build output), .env.local (secret keys),
    .DS_Store, and the two stray files that were sitting in this
    folder before the app existed (files.zip, Claude (1).dmg).

.env.local
    Holds two secrets: the Supabase project URL and its "anon" public
    key. Read automatically by Next.js at build/run time. NOT in git —
    each developer (or each deployment) needs their own copy of this
    file with real values.

next-env.d.ts
    Auto-generated by Next.js, makes TypeScript aware of Next's global
    types. Never hand-edited.


------------------------------------------------------------
3. THE APP ITSELF (src/app — one folder per URL route)
------------------------------------------------------------

src/app/layout.tsx
    The wrapper around every single page: sets up the fonts, the
    <html>/<body> tags, and the browser tab title ("Project Vault").
    Every route below renders *inside* this.

src/app/page.tsx
    The homepage, at "/". Currently just the plain "Project Vault"
    heading — intentionally bare, this was Prompt 1's entire scope.

src/app/globals.css
    Site-wide styles; this is where Tailwind gets switched on.

src/app/login/page.tsx
    The "/login" page. A single email field. Submitting it calls
    Supabase's signInWithOtp function, which emails the user a
    one-time sign-in link. Runs entirely in the browser (marked
    "use client").

src/app/auth/confirm/route.ts
    Not a page — a route the *email link* points to, at
    "/auth/confirm". When clicked, this code verifies the token from
    the email and turns it into a real logged-in session, then
    redirects the user on to "/projects". This is what Prompt 4 refers
    to as the piece that makes "click the link → land on /projects"
    work.

src/app/auth/signout/route.ts
    Another non-page route, at "/auth/signout". The sign-out button on
    /projects submits a form here; this clears the Supabase session
    and sends the user back to "/login".

src/app/projects/page.tsx
    The "/projects" page. Right now it's a placeholder: it shows the
    signed-in user's email and a sign-out button. Prompt 5 (not built
    yet) will replace this with the real projects list and a "New
    project" button. This page also double-checks login status itself
    (on top of the proxy check below) and redirects to /login if
    nobody's signed in — belt and braces.

src/proxy.ts
    Runs before almost every page request (this is Next.js's newest
    name for what used to be called "middleware"). Its job: ask
    Supabase "who's logged in?" and, if nobody is and the URL starts
    with "/projects", redirect to "/login" before the page even
    starts rendering. This is the actual mechanism behind "visiting
    /projects while logged out redirects to /login" from Prompt 4.

src/lib/supabase/middleware.ts
    The actual logic proxy.ts calls. Talks to Supabase using the
    request's cookies to figure out the current session, and refreshes
    that session's cookies so logins don't silently expire.

public/*.svg, src/app/favicon.ico
    Static image assets Next.js's starter template ships with by
    default (logos, icons). Not used anywhere in the actual UI yet —
    leftover from the initial scaffold.


------------------------------------------------------------
4. THE SUPABASE CONNECTION (src/lib/supabase)
------------------------------------------------------------

src/lib/supabase/client.ts
    Creates a connection to Supabase for use in the BROWSER (inside
    components marked "use client", like the login form). Reads the
    URL/key from .env.local via process.env.

src/lib/supabase/server.ts
    Creates a connection to Supabase for use on the SERVER (Server
    Components, route handlers like auth/confirm and auth/signout).
    Reads/writes login-session cookies so the server always knows who
    (if anyone) is logged in on a given request.

Both files do the same conceptual thing — "give me a way to talk to
Supabase" — but browser code and server code need different mechanics
under the hood (mainly: how cookies get read and written), which is
why there are two versions instead of one.


------------------------------------------------------------
5. THE DATABASE (supabase/schema.sql)
------------------------------------------------------------

This file is NOT run automatically — it's a script that gets manually
pasted into the Supabase dashboard's SQL Editor. It currently defines
two tables:

projects
    id, name, deadline, org_id, created_at.
    One row per student group project. org_id is an empty placeholder
    column for now — no organizations table exists yet — reserved for
    when the product needs to isolate different universities/orgs from
    each other.

members
    project_id, user_id, role.
    Who belongs to which project, and their role (e.g. "owner"). Links
    to Supabase's own built-in auth.users table, so it's tied to real
    accounts once someone actually logs in.

Both tables have Row Level Security turned ON with no policies written
yet. In plain terms: right now, the database will refuse to let
ANYONE read or write these tables through the API, logged in or not.
That's deliberate — it's the safe default until Prompt 4+ work defines
real rules like "a user can only see projects they belong to." Nothing
breaks today because no page queries these tables yet.


------------------------------------------------------------
6. HOW A REQUEST ACTUALLY FLOWS, END TO END
------------------------------------------------------------

Example: a brand new user tries to visit /projects.

  1. Browser requests "/projects".
  2. src/proxy.ts runs first. It asks Supabase (via
     src/lib/supabase/middleware.ts) "is this browser logged in?"
     using whatever cookies came with the request.
  3. No session cookie exists yet, so proxy.ts redirects the browser
     to "/login" before src/app/projects/page.tsx ever runs.
  4. User types their email into src/app/login/page.tsx and submits.
     That calls Supabase directly (via src/lib/supabase/client.ts)
     and asks it to email a magic link.
  5. Supabase sends an email. The link inside it points at
     "https://<site>/auth/confirm?token_hash=...&type=email".
  6. User clicks it. src/app/auth/confirm/route.ts runs on the server,
     verifies the token via src/lib/supabase/server.ts, and Supabase
     sets real session cookies in the response.
  7. That route redirects to "/projects" again. This time proxy.ts
     sees a valid session and lets the request through.
  8. src/app/projects/page.tsx renders, itself re-checking the session
     via src/lib/supabase/server.ts, and shows the signed-in email +
     sign-out button.
  9. Clicking "Sign out" submits a form to
     src/app/auth/signout/route.ts, which clears the session and
     sends the user back to "/login".

The supabase/schema.sql tables (projects, members) aren't touched
anywhere in this flow yet — they exist in the database, locked by Row
Level Security, waiting for Prompt 5 onward to actually query them.
